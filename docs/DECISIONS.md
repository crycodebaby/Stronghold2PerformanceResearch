# DECISIONS

> Kurzfassung: Warum wir etwas so machen (D###): Entscheidung, Begründung, verworfene Alternativen.

Format: ID · date · decision · rationale · rejected alternatives.

## D001 · 2026-10-15 · Patch/hook the original, not reimplement
- Decision: Improve performance via measurement, hooks and patches on `Stronghold2.exe`. Reimplementation = long-term vision.
- Rationale: ~1,300 game classes / 5 MB code; cause of slowdown unmeasured; proprietary middleware (Granny, LifeStudio); lockstep determinism makes bit-exact reimplementation very hard.
- Rejected: full open-source clone now (years, unclear payoff before knowing the hotspot).

## D002 · 2026-10-15 · Separate project repo, AnalyseHub stays its own repo
- Decision: `SH2-Perf` holds docs + small tools; `Stronghold2AnalyseHub` (upstream crycodebaby) gets changes on branch `perf-metrics`.
- Rationale: keeps upstream history clean, allows PR upstream; docs independent of DLL code.
- Rejected: vendoring AnalyseHub into SH2-Perf (loses upstream link); git submodule (extra friction now, can add later).

## D003 · 2026-10-15 · CMake build for AnalyseHub
- Decision: add `CMakeLists.txt` (Win32, Release, static CRT).
- Rationale: upstream `.sln` references no project (no `.vcxproj` in repo) → not buildable as-is. CMake is scriptable from CLI.
- Rejected: hand-written `.vcxproj` (verbose, hard to review).

## D004 · 2026-10-15 · Load AnalyseHub via launcher injection, not d3d9.dll proxy
- Status: **superseded by D009** (2026-10-15). Launcher kept as fallback.
- Decision: `SH2Launcher.exe` starts the game suspended, injects the DLL (`LoadLibraryW` via remote thread), waits for a ready event, resumes.
- Rationale: DXVK test (EXP-003) needs `d3d9.dll` in the game folder → a d3d9 proxy would collide. Hook must be installed before the game calls `Direct3DCreate9` → suspended start.
- Rejected: d3d9 proxy (DXVK conflict); attach-after-start injection (misses `Direct3DCreate9`).

## D005 · 2026-10-15 · Measurement first, game-code hooks later
- Decision: phase 1 instruments only D3D9 (counters, timings). No hooks into game functions until profiling data (EXP-001) points at a hotspot.
- Rationale: user requirement; avoids guesswork.
- Rejected: speculative hooks on pathfinder.

## D006 · 2026-10-15 · Bronze / silver / gold data layers
- Decision: `captures/` (bronze: raw CSV, logs, Ghidra exports; gitignored) → `data/` (silver: `index.jsonl` one metrics line per capture, tracked; `vtables.db` rebuilt by `sym.py build`) → `docs/` (gold: curated). Tools move data between layers (`ingest.py`, `sym.py`); the hub writes into a configurable dir (`SH2Launcher --out`, default `TEST\SH2Perf_out`) plus `latest.json`.
- Rationale: raw data never enters agent context; comparisons run on small structured lines; captures are reproducible via `meta.json` (hashes, variant, hub commit, CPU/GPU).
- Rejected: CSVs in git (size, personal data); a database server (overkill); hub writing next to the exe (mixes game and data files).

## D007 · 2026-10-15 · Remove personal paths before publishing raw data
- Decision: raw logs/CSVs (`captures/`) may contain absolute paths (the hub log lists every loaded module path incl. user name). Before any upload, issue attachment or release they are scrubbed (replace `<drive>:\Users\<name>` with `%USERPROFILE%`). `data/` and all `*.md` must never contain absolute user paths — enforced by `lint_docs.py`.
- Rationale: privacy; repo may become public.
- Rejected: stripping paths in the hub (module paths are the evidence for F032 locally).

## D008 · 2026-10-15 · Function analysis through structural briefs
- Decision: agents analyse functions via `tools/sym.py` + `tools/fbrief.py` (addresses, sizes, callers/callees, loops, strings). Decompiled code stays inside Ghidra — not in the repo, not in agent context.
- Rationale: legal (no decompiled code in repo/releases), context budget, briefs are diffable facts.
- Rejected: pasting pseudocode into docs/context.

## D009 · 2026-10-15 · Load AnalyseHub via d3d9.dll proxy (chains to system d3d9 or DXVK)
- Decision: default loader is a `d3d9.dll` proxy in the TEST folder (hub repo `proxy/`). It loads the real d3d9 (`target=system` → system dir, or `target=d3d9_dxvk.dll` = renamed DXVK) and then `Stronghold2AnalyseHub.dll`; its `Direct3DCreate9` waits (≤ 15 s) until the hub reports its hook. Config `SH2Proxy.ini` (`target`, `hub`, `hubdll`, `out`), env overrides `SH2HUB_DISABLE=1`, `SH2HUB_OUT`. `hub=0` = pass-through without recompiling. `tools/variant.py` installs proxy + hub copy + ini for every variant and places DXVK as `d3d9_dxvk.dll`. The hub logs the exe sha256 and `known build: yes/no` (F058), log only.
- Rationale: game starts normally (double-click), no suspended process, no remote thread; D004's objections are resolved: DXVK conflict → chaining via `target`; hook timing → the proxy owns the export the game calls. The observed launcher failure (F080) is **not** the reason: it was a hub bug (F081), fixed in the hub; cause in game still to confirm (F082).
- Details: real exports resolved at runtime (17 named exports of system d3d9 = DXVK 3.1.1), naked jump stubs; nothing loaded under loader lock (starter thread); the hub finds the real module through the proxy export `SH2Proxy_RealModule` (two modules named d3d9.dll are loaded); `target` pointing at the proxy itself is refused.
- Rejected: launcher only (extra start step, suspended start fragile); static `.def` forwarders (fixed target, no DXVK switch without rebuild); loading the hub inside `DllMain` (loader lock); DXVK's own `d3d9.dll` slot with hub injection (needs the launcher again).

## D010 · 2026-10-15 · Build the sampling profiler (module split first) before EXP-001
- Decision: implement the hub sampler now, starting with a per-module count of the render thread (exe, dragonfly, dxrenderer, d3d9, driver, granny2), functions second. Default off (`sample=off`), switched by `variant.py sample`.
- Rationale: EXP-001-REAL-B shows the render thread at 98 % with the army in view, running +10.7 ms over pause (F098), but counters cannot say whether the time is game code or graphics driver (F102). The KNIGHTS scenario does not exist yet, the real lag save does. Replaces the trigger "only after EXP-001" in the design.
- Consequences: the sampler suspends the render thread ~100×/s for ~30 µs (intervention, measured 2–4 % in a synthetic test): every profiler run needs an unprofiled comparison run; FPS from a sampled run are not used as baseline. Read-only otherwise (D005 holds: no game-code hooks).
- Rejected: WPR/ETW as the first tool (no exe symbols, kernel-level setup; kept as cross-check); 1 kHz sampling (overhead); hooking guessed functions (D005).

## D011 · 2026-10-15 · Measurement path off the render thread, four independent switches
- Decision: (1) The render thread only copies a fixed record per frame into a bounded wait-free ring (8,192 slots); a low-priority capture thread formats CSV, writes files, polls thread CPU / address space (only while recording), runs start/stop work (sampler CSV, `latest.json`). A full ring drops the record and counts it; nothing waits. Overflows and write errors are logged, shown in the overlay and written to `latest.json` (`capture_ok`, `frames_dropped`, `frames_lost_write`, `write_errors`). (2) Four switches decide which hooks exist at all: `frametime` (Present), `counters` (8 draw/state slots), `poll` (background queries), `overlay` (EndScene + Reset + WndProc); plus `beep`. Defaults = `full` profile (behaviour of earlier hub builds, now with the work off the render thread); `min` = frame time only. Source: env `SH2HUB_<KEY>` > `SH2Proxy.ini` > profile; `variant.py mode|switch`. (3) CSV columns unchanged; `latest.json` gains `capture_version: 2` and `modes`. Values of a switched-off part are 0 in the CSV and `null` in the index line (`ingest.py`). Captures before this have neither key and count as all-on, capture OK.
- Rationale: the lag captures show long frames on a 1 s clock (F104) and the old hub did its file/CPU-query work once per second on the render thread (F105); a stand-in reproduces such hitches with the old build and not with the new one (F106). The cause in the game is still a hypothesis (F107) and is decided by an in-game A/B (EXPERIMENTS.md). Independent switches make the remaining influence of each part testable instead of assumed.
- Consequences: `min` has no EndScene timing, so `cpu-side` is not comparable across modes: compare `frame_ms` and `present_ms` only (`tools/ab_compare.py`). The ring needs ~0.9 MB of the game's 2 GB address space. `Recording()` stays true until files and `latest.json` are complete. `SH2HUB_SAMPLE` stays a separate switch.
- Rejected: one global "light mode" flag (hides which part costs what); a mutex-protected queue (the render thread could block behind a slow writer); writing from the render thread with a larger buffer (the periodic flush stays); changing the CSV format (breaks `ingest.py`/index history).

## D012 · 2026-10-15 · One manifest per recording, safe import, silver rebuildable from bronze
- Decision: (1) The hub writes `<stem>_manifest.json` for every recording (capture id, session, plan, game speed/pause with origin, software identity with full SHA-256 taken when the hub was loaded in the session, effective switches with source, file list with sizes and hashes, technical quality). Status `recording` is written before the first frame, `finalized` only after all files are closed and hashed; a manifest stuck at `recording` marks an interrupted recording. `latest.json` stays as a pointer (`capture_version 3`). All file/hash/JSON work runs on the capture thread or a background hashing thread, never on the render thread. (2) `ingest.py` imports in three steps — verify (read-only), stage (`captures/.staging/<id>/`), commit (one atomic directory rename) — never deletes or moves sources, never changes existing bronze, is idempotent per capture id and reports a different content under the same id as a conflict. (3) Derived results go to `data/silver/<id>/` + `data/index.jsonl`; user facts (confirmed speed/pause, labels, suitability) go to `data/annotations/<id>.json`; silver is a pure function of bronze + annotations + tool version (`ingest.py rebuild`). (4) Game speed and pause are numbers/booleans with origin `planned` / `user_confirmed` / `observed` / `unknown`; the hub never reads game memory, so only `planned` (from `variant.py plan`) is produced automatically and `user_confirmed` only by the user. No valid range or meaning is assumed. (5) Technical quality and benchmark suitability are separate; legacy recordings are `unknown`/unverified, not fault-free and not "all switches on".
- Rationale: `latest.json` names only the newest recording and mixed up which modes, commit and hashes belonged to which file (recording set aside on 2026-10-15; hashes were taken at ingest time, after a rebuilt hub could already have replaced the DLL). Old `ingest.py` deleted the sources after copying and made folder names from labels (`_2` suffix), so a repeat or a crash could lose or duplicate data.
- Consequences: new capture ids (`rec-…`) replace `<date>_<exp>_<variant>_<scenario>` for new imports; labels live in annotations. Old folders stay as they are. Sources must be deleted by hand. Hashes of the game folder at import time are only compared with the recorded identity (`software_changed_after_capture`), never stored as provenance. The config file is not part of the software comparison (its content is recorded as `switches`).
- Rejected: a database or service (out of scope); hashing at import time as provenance (cannot show what ran); parsing JSON in the hub (plan comes from the ini, the prepared record is copied as a file); guessing a speed range or reading speed from unknown game addresses (D005); deleting sources after a verified import (user decision); one big transaction log instead of the atomic rename.

## D013 · 2026-10-15 · Enforce the D012 protections: reference profile, verified bronze, write lock, name rules, safe deactivation
- Decision: (1) Benchmark use is judged in three separate steps — integrity, description against the single profile `reference-v1` (experiment, scenario, variant, game speed known and uncontradicted, switches known, session hashes of exe and hub DLL, pause known for every phase) and the user's release. A release never overrules the other two; every failure is a coded, readable rejection. A global pause statement counts for a one-phase recording only; phases of a mixed recording stay unknown until the user confirms each (`annotate --phase-paused`). (2) One integrity check against `import.json` guards `verify`, a repeated import, `annotate` and every derivation of silver; a damaged capture stops with exit 4, earlier silver is kept but marked `INVALID`, bronze is never repaired. (3) `import`, `annotate` and `rebuild --write` run under one OS file lock (`data/.sh2perf.lock`, released by the OS when its process ends); busy = wait `--lock-timeout`, then exit 7 with nothing changed; under the lock a staging folder of the own id is a dead process's leftover. (4) Manifest names and roles are validated before any write (plain Windows names, reserved importer names, Windows-equal duplicates, known unique roles, exactly one frames file); cleanup only through `safe_rmtree` (direct non-link child of `.staging`). (5) Deactivation (END), not unload: every background thread (capture writer, sampler, hashing) is asked to stop and must really END before the DLL may go; a handle close is no proof; on timeout nothing is released, the state is logged (`Unload DEFERRED`) and the hub stays loaded and keeps waiting without killing anything. Hooks: `Uninstall` makes them inert, only the render thread tears ImGui down, trampolines are not freed, and once hooks were installed the DLL stays mapped until the process ends (only its init thread ends): END **deactivates** the hub, it does not unload it; activating it again or using another hub build needs a game restart. Overlay, log (`Hub deactivated …`) and guides say so. A normal exit of the game does **not** finalize an open recording (F117); only F9/END do, so: F9 stop, wait for `Recording stopped … manifest published`, then quit. Automatic finalization at game end was deliberately not built (no new hooks, no work in `DllMain`).
- Rationale: the first D012 cut let a manual "suitable" overrule unknown or contradicting speed, trusted `import.json` without looking at bronze, let parallel processes delete each other's staging folders and lose index lines, accepted names like `manifest.json` or `CON` from a manifest, and closed the capture event and returned from `Shutdown` while threads still ran. A stand-in run additionally showed the END deactivation crashing the program (3 of 4 runs with the build before this order, 4 of 4 after the thread fix alone): ImGui was destroyed by the init thread while the render thread drew with it, and EndScene re-created it.
- Consequences: the three existing captures and any recording without full description are never "usable"; the reference profile is the only rule set and is extended only by a new decision. The hub DLL is never unmapped after hook installation: a hub update needs a game restart (it did before in practice, the proxy loads it at start). A permanently blocked writer keeps the unload deferred until the process ends.
- Rejected: automatic repair or re-copy of damaged bronze; PID lock files (stale after a crash); `TerminateThread`; unloading the DLL after a timeout "to be tidy"; per-call counters in all hooks to drain in-flight calls (cost in the render path); a general rule engine for benchmark suitability.

## D014 · 2026-10-15 · EXP-008 observes Granny at the exe import table, aggregated, render thread only
- Decision: the Granny observer redirects six slots of Stronghold2.exe's import address table for granny2.dll to stdcall thunks with the verified signatures (F137); it is a separate hub switch `granny`, default off, outside the `full`/`min` profiles. Each thunk forwards exactly once with unchanged arguments (clock as raw bits) and return value. While recording, only the render thread updates preallocated tables (per object × marker aggregates, one row per frame, change counts, deform → instance links through observed world-pose / composite pointers); other threads are counted only. Output at stop: four files with manifest roles `granny_*` (docs/FORMATS/GRANNY_OBSERVER.md).
- Rationale: the exe calls these functions only through `call [IAT]`, so a slot swap needs no code patch in either module, is atomic, reversible at END and leaves granny2.dll byte-identical; the deform call carries no model instance (F138), so a link has to come from observed pointers and stays classified (frame / older / none / ambiguous). Aggregates instead of per-call logs keep the render thread free of files and allocation (D011) and bound memory.
- Consequences: calls inside granny2.dll and from other modules are invisible; control clocks/speeds/weights and pointed-to data are not observed, so "unchanged observed values" never means "identical results"; pointer ids are per session and reuse without an observed free is undetectable; ≈ 6.6 MB committed while observing; frame times of observed runs are "under observation" until the off/on rule says otherwise.
- Rejected: MinHook detours inside granny2.dll (patches library code, would also see internal calls but changes code bytes); per-call event logs (unbounded, file/heap pressure); reading deform matrices or vertex buffers (large reads, GPU-adjacent memory); a cache or skip experiment (out of scope until F136 is answered).
